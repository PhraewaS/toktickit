# REST API Contract ของ TokTickIT Lab 3

Base URL: `/api` โดย success response ของ JSON ใช้รูปแบบ `{ "data": ... }` และ error ใช้รูปแบบ `{ "error": { "code", "message", "fields"? } }` วันที่ใช้ ISO 8601 UTC server จะไม่ส่ง password hashes, session tokens, stored filenames, filesystem paths, SQL หรือ stack traces กลับไป

## การยืนยันตัวตน

`POST /auth/login` รับ body `{email,password}` เมื่อสำเร็จตอบ `200` เป็น `{data:{user:{id,name,email,role,isActive,mustChangePassword}}}` และตั้งค่า HttpOnly `toktickit_session` cookie credentials ไม่ถูกต้องหรือผู้ใช้ inactive ตอบ `401 AUTHENTICATION_FAILED` โดยไม่เปิดเผยว่าเกิดจากสาเหตุใด

`GET /auth/me` ตอบ `200 {data:{user}}` สำหรับ session ที่ถูกต้องและมี `mustChangePassword`, ตอบ `401 AUTHENTICATION_REQUIRED` เมื่อไม่มี cookie และ `401 SESSION_INVALID` เมื่อ cookie หมดอายุหรือไม่รู้จัก `POST /auth/logout` ตอบ `200 {data:{loggedOut:true}}`, ทำให้ session ปัจจุบันใช้ไม่ได้และล้าง cookie; endpoint นี้ใช้ได้ระหว่าง first-login gate และตอบ `401 AUTHENTICATION_REQUIRED` เมื่อไม่มี session `POST /auth/change-password` รับ body `{newPassword,confirmPassword}` ตอบ `200 {data:{user}}` สำหรับผู้ใช้ที่มี initial password, ตั้ง `mustChangePassword=false` และปลด gate กรณีข้อมูล password ขาด ไม่ตรงกัน หรือไม่แข็งแรงตอบ `400 VALIDATION_ERROR` พร้อมรายละเอียด field; session ขาดหรือไม่ถูกต้องตอบ `401 AUTHENTICATION_REQUIRED`/`401 SESSION_INVALID` Password ต้องมีความยาว 12-128 ตัวอักษร และต้องมีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก ตัวเลข และสัญลักษณ์

สำหรับ protected route อื่นทั้งหมด server ต้อง authenticate session ก่อน หาก session ถูกต้องแต่ผู้ใช้ยังมี `mustChangePassword=true` ให้ตอบ `403 {error:{code:"PASSWORD_CHANGE_REQUIRED",message}}` ก่อนตรวจ role, ownership, validation หรือ resource ของ route นั้น และห้ามทำ read/mutation ตามปกติ gate นี้ไม่ใช้กับ `GET /auth/me`, `POST /auth/logout` และ `POST /auth/change-password`; หลังเปลี่ยน password สำเร็จ protected-route behavior จึงกลับมาเป็นปกติ

## Requester routes

Lab 2 routes เดิม: `GET /development-requesters` ถูก retire ใน production และตอบ `410 {error:{code:"DEVELOPMENT_REQUESTERS_RETIRED",message}}` ใน production ไม่ว่า flags จะเป็นอย่างไร จะเปิดได้เฉพาะเมื่อ `NODE_ENV` ไม่ใช่ production และ process ที่ระบุชัดเจนว่าเป็น regression/migration tooling ตั้งค่า `LAB2_COMPATIBILITY_MODE=true` เท่านั้น endpoint นี้ไม่ใช่ authenticated identity source และ Lab 3 client จะไม่เรียกใช้ Authenticated Requester ใช้ `POST /tickets`, `GET /tickets`, `GET /tickets/:ticketId` และ attachment list/upload/download/remove routes โดยไม่ส่ง requester header server จะ derive `requesterId` จาก session response shapes เดิมและ safe 404 ownership behavior ยังคงเดิม ส่วน protected Requester routes ตอบ `401 AUTHENTICATION_REQUIRED`/`401 SESSION_INVALID` ก่อนตรวจ ownership

`GET /tickets/:ticketId/comments` ตอบ `200 {data:{items:[comment...]}}` และ `POST /tickets/:ticketId/comments` รับ body `{content}` แล้วตอบ `201 {data:{comment}}` สำหรับ authenticated Requester ที่เป็นเจ้าของ ticket เนื้อหาว่าง เป็น whitespace หรือเกิน limit ตอบ `400 INVALID_CONTENT`; session ขาดหรือไม่ถูกต้องตอบ `401 AUTHENTICATION_REQUIRED`/`401 SESSION_INVALID`; ticket ของผู้อื่นหรือ ticket ที่ไม่มีอยู่ตอบ safe `404 TICKET_NOT_FOUND`; unexpected failures ตอบ `500 INTERNAL_ERROR`

`POST /tickets/:ticketId/resolved` รับ body `{}` และตอบ `200 {data:{ticketId,requesterResolvedAt,currentStatus}}` สำหรับ authenticated Requester ที่เป็นเจ้าของ ticket operation นี้เป็น idempotent บันทึก resolved indication ของ Requester และไม่เปลี่ยน formal ticket status ticket ID ไม่ถูกต้องหรือ body มีรูปแบบผิด/field ที่ไม่คาดไว้ตอบ `400 INVALID_TICKET_ID`/`400 VALIDATION_ERROR`; session ขาดหรือไม่ถูกต้องตอบ `401 AUTHENTICATION_REQUIRED`/`401 SESSION_INVALID`; ticket ของผู้อื่นหรือ ticket ที่ไม่มีอยู่ตอบ safe `404 TICKET_NOT_FOUND`; IT Staff, Administrator และ role อื่นที่ไม่ใช่ Requester ตอบ `403 ROLE_FORBIDDEN`; session ที่ผ่านการ authenticate แล้วแต่ติด first-login gate ตอบ `403 PASSWORD_CHANGE_REQUIRED` ก่อนผล route-specific เหล่านี้; persistence failure ตอบ `500 INTERNAL_ERROR`

## IT Staff routes

`GET /staff/tickets` รับ `search` (ticket number หรือ summary), `status`, `requestedPriority`, `itPriority`, `ownerId`, `sortBy` (`ticketNumber|summary|createdAt|updatedAt|itPriority|currentStatus`), `sortOrder` (`asc|desc`), `page` (ค่าเริ่มต้น 1) และ `pageSize` (10, 20, 50) IT Staff และ Administrator ได้รับ HTTP `200` พร้อม envelope `{data:{items:[staffTicket...],pagination:{page,pageSize,totalItems,totalPages}}}` โดย `id asc` เป็น tie-breaker ของทุก sort order filters ไม่ถูกต้องตอบ `400 INVALID_QUERY`; page ที่ไม่มีอยู่ตอบ `400 PAGE_OUT_OF_RANGE`; session ขาด/ไม่ถูกต้องตอบ `401 AUTHENTICATION_REQUIRED`/`401 SESSION_INVALID`; role อื่นที่ authenticate แล้วตอบ `403 ROLE_FORBIDDEN`; read failure ที่ไม่คาดไว้ตอบ `500 INTERNAL_ERROR`. Client API wrapper จะ unwrap outer `data` และส่งต่อให้ UI เป็น `{items,pagination}` เท่านั้น จึงห้ามใช้ mock หรือ component shape แบบ `{data,pagination}`

`GET /staff/tickets/:ticketId` ตอบ `200 {data:staffTicketDetail}` สำหรับ IT Staff และ Administrator ID ไม่ถูกต้องตอบ `400 INVALID_TICKET_ID`; ticket ไม่มีอยู่ตอบ `404 TICKET_NOT_FOUND`; Requester หรือ role ที่ไม่ใช่ staff ตอบ `403 ROLE_FORBIDDEN`; session ขาด/ไม่ถูกต้องตอบ `401` Internal Notes จะถูกรวมเฉพาะใน response ของ staff-visible roles เท่านั้น read failure ตอบ `500 INTERNAL_ERROR`

`POST /staff/tickets/:ticketId/assignment` รับ body `{ownerId:number|null}` เพื่อ claim, assign หรือ unassign ticket และตอบ `200 {data:staffTicketDetail}` ID ไม่ถูกต้องตอบ `400 INVALID_TICKET_ID`; owner ID รูปแบบผิดตอบ `400 VALIDATION_ERROR`; `ownerId` ต้องเป็น null หรือ active IT Staff/Administrator มิฉะนั้นตอบ `400 INVALID_OWNER`; ticket ไม่มีอยู่ตอบ `404 TICKET_NOT_FOUND` session ขาด/ไม่ถูกต้องตอบ `401`; Administrator และ role อื่นที่ไม่ใช่ IT Staff ตอบ `403 ROLE_FORBIDDEN` เพราะมีเพียง IT Staff ที่ทำ assignment ได้; persistence failure ตอบ `500 INTERNAL_ERROR`

`PATCH /staff/tickets/:ticketId/priority` รับ body `{itPriority}` และตอบ `200 {data:staffTicketDetail}` สำหรับ IT Staff และ Administrator ID ไม่ถูกต้องหรือ priority ขาด/ไม่รองรับตอบ `400 INVALID_TICKET_ID`/`400 VALIDATION_ERROR`; ticket ไม่มีอยู่ตอบ `404 TICKET_NOT_FOUND`; Requester หรือ role อื่นที่ไม่ใช่ staff ตอบ `403 ROLE_FORBIDDEN`; session ขาด/ไม่ถูกต้องตอบ `401`; persistence failure ตอบ `500 INTERNAL_ERROR`

`PATCH /staff/tickets/:ticketId/status` รับ body `{status}` และตอบ `200 {data:staffTicketDetail}` เมื่อเป็น transition ที่อนุญาตเท่านั้น ID ไม่ถูกต้องหรือ status ไม่รู้จักตอบ `400 INVALID_TICKET_ID`/`400 VALIDATION_ERROR`; transition ที่อยู่นอก BR-10 ตอบ `409 STATUS_TRANSITION_NOT_ALLOWED`; ticket ไม่มีอยู่ตอบ `404 TICKET_NOT_FOUND`; role ที่ไม่ใช่ IT Staff ตอบ `403 ROLE_FORBIDDEN`; session ขาด/ไม่ถูกต้องตอบ `401`; persistence failure ตอบ `500 INTERNAL_ERROR`

`GET /staff/tickets/:ticketId/comments` ตอบ `200 {data:{items:[comment...]}}` และใช้ได้กับ IT Staff และ Administrator ที่มี ticket visibility ส่วน `POST /staff/tickets/:ticketId/comments` รับ body `{content}` และตอบ `201 {data:{comment}}` สำหรับ IT Staff เท่านั้น เนื้อหาว่าง เป็น whitespace หรือเกิน limit ตอบ `400 INVALID_CONTENT`; ticket ID ไม่ถูกต้อง/ขาดตอบ `400 INVALID_TICKET_ID`; ticket ไม่มีอยู่ตอบ `404 TICKET_NOT_FOUND`; Administrator ที่ POST ตอบ `403 ROLE_FORBIDDEN`; session ขาด/ไม่ถูกต้องตอบ `401`; persistence failure ตอบ `500 INTERNAL_ERROR`

`GET /staff/tickets/:ticketId/notes` ตอบ `200 {data:{items:[note...]}}` สำหรับ IT Staff และ Administrator ส่วน `POST /staff/tickets/:ticketId/notes` รับ body `{content}` และตอบ `201 {data:{note}}` สำหรับ IT Staff เท่านั้น ใช้ content validation เดียวกัน โดยตอบ `400 INVALID_CONTENT`, `400 INVALID_TICKET_ID`, `404 TICKET_NOT_FOUND`, `403 ROLE_FORBIDDEN` สำหรับ Administrator POST, `401` เมื่อ session ขาด/ไม่ถูกต้อง และ `500 INTERNAL_ERROR` เมื่อ persistence failure Notes เป็น append-only

## Administrator routes

`GET /admin/users` รับ `search` และ `role` แบบ optional และตอบ `200 {data:[user...]}` ค่า role/query ไม่ถูกต้องตอบ `400 INVALID_QUERY`; session ขาด/ไม่ถูกต้องตอบ `401`; role ที่ไม่ใช่ Administrator ตอบ `403 ROLE_FORBIDDEN`; read failure ตอบ `500 INTERNAL_ERROR`

`POST /admin/users` รับ body `{name,email,role,isActive,initialPassword}` ตอบ `201 {data:{user}}` และไม่ส่ง password หรือ hash กลับมา field ขาด/ไม่ถูกต้องตอบ `400 VALIDATION_ERROR` พร้อม safe `fields`; email ซ้ำแบบไม่สนตัวพิมพ์ตอบ `409 DUPLICATE_EMAIL`; role ที่ไม่ใช่ Administrator ตอบ `403 ROLE_FORBIDDEN`; persistence failure ตอบ `500 INTERNAL_ERROR`

`PATCH /admin/users/:userId` รับ body ที่อาจมี `name,email,role,isActive` และตอบ `200 {data:{user}}` ID ไม่ถูกต้องตอบ `400 INVALID_USER_ID`; malformed body หรือ field ที่มีชนิด/รูปแบบ/ค่าไม่ถูกต้อง เช่น name ว่าง, email ไม่ถูกต้อง, role ไม่รองรับ หรือ isActive ไม่ใช่ boolean ตอบ `400 VALIDATION_ERROR` พร้อม safe `fields`; user ไม่มีอยู่ตอบ `404 USER_NOT_FOUND`; email ซ้ำแบบ case-insensitive ตอบ `409 DUPLICATE_EMAIL`; self-deactivation หรือการทำให้เหลือ active Administrator ไม่ถึงหนึ่งคนตอบ `409 USER_UPDATE_CONFLICT` พร้อม safe conflict details; role ที่ไม่ใช่ Administrator ตอบ `403 ROLE_FORBIDDEN`; persistence failure ตอบ `500 INTERNAL_ERROR` เมื่อ update `isActive` จาก true เป็น false สำเร็จ ระบบต้อง revoke sessions ของ target ทั้งหมด และ request ถัดไปด้วย session เดิมต้องตอบ `401 SESSION_INVALID`

`POST /admin/users/:userId/initial-password` รับ body `{initialPassword}` ตอบ `200 {data:{user}}`, invalidate sessions ของ target และตั้ง `mustChangePassword=true` ID ไม่ถูกต้องตอบ `400 INVALID_USER_ID`; password ไม่ถูกต้องตอบ `400 VALIDATION_ERROR`; user ไม่มีอยู่ตอบ `404 USER_NOT_FOUND`; role ที่ไม่ใช่ Administrator ตอบ `403 ROLE_FORBIDDEN`; persistence failure ตอบ `500 INTERNAL_ERROR` โดย response จะไม่รวม initial password

## Status codes และ security

`200` ใช้กับ retrieve/update, `201` ใช้กับ create, `400` ใช้กับ invalid input, `401` ใช้กับ unauthenticated หรือ authentication failure, `403` ใช้กับ authenticated แต่ไม่มีสิทธิ์หรือ `PASSWORD_CHANGE_REQUIRED`, `404` ใช้กับ resource ที่ไม่มีอยู่หรือเป็น protected-other-owner, `409` ใช้กับ conflict, `410` ใช้กับ retired compatibility endpoint และ `500` ใช้กับ unexpected failure แบบปลอดภัย `LAB2_COMPATIBILITY_MODE` ใช้ได้เฉพาะ non-production regression/migration tooling และไม่มีผลใน production state-changing browser requests ต้องใช้ same-site origin เมื่อมี Origin header และ Internal Notes จะไม่ถูกเลือกใส่ใน Requester responses
